# 보안 정책

## 개요

Claude How To 프로젝트는 보안을 중요하게 생각합니다. 이 문서는 우리의 보안 관행과 취약점을 책임감 있게 보고하는 방법을 정합니다.

## 지원 대상 버전

다음 버전에 대해 보안 업데이트를 제공합니다:

| 버전 | 상태 | 지원 기한 |
|---------|--------|---------------|
| Latest(main) | ✅ 활성 | 현재 + 6개월 |

**참고:** 교육용 가이드 프로젝트인 만큼, 우리는 전통적인 버전 지원보다 최신 모범 사례와 문서 보안을 유지하는 데 중점을 둡니다. 업데이트는 main 브랜치에 직접 적용됩니다.

## 보안 관행

### 코드 보안

1. **의존성 관리**
   - 모든 Python 의존성은 `requirements.txt`에 고정됩니다
   - Dependabot과 수동 리뷰를 통한 정기 업데이트
   - 모든 커밋에서 Bandit으로 보안 스캔
   - 보안 검사용 pre-commit 훅

2. **코드 품질**
   - Ruff 린팅이 일반적인 문제를 잡아냅니다
   - mypy 타입 검사로 타입 관련 취약점을 방지합니다
   - pre-commit 훅이 표준을 강제합니다
   - 모든 변경은 머지 전에 리뷰됩니다

3. **접근 제어**
   - `main` 브랜치의 브랜치 보호
   - 머지 전 필수 리뷰
   - 머지 전 상태 검사 통과 필수
   - 저장소 쓰기 권한 제한

### 문서 보안

1. **예시에 시크릿을 포함하지 않음**
   - 예시 속 API 키는 모두 플레이스홀더입니다
   - 인증 정보를 하드코딩하지 않습니다
   - `.env.example` 파일로 필요한 변수를 보여 줍니다
   - 시크릿 관리에 관한 명확한 경고

2. **보안 모범 사례**
   - 예시는 안전한 패턴을 보여 줍니다
   - 문서에서 보안 경고를 강조합니다
   - 공식 보안 가이드로의 링크
   - 관련 섹션에서 인증 정보 취급을 다룹니다

3. **콘텐츠 리뷰**
   - 모든 문서를 보안 문제 관점에서 리뷰
   - 기여 가이드라인에 보안 고려 사항 포함
   - 외부 링크와 참조 검증

### 의존성 보안

1. **스캔**
   - Bandit이 모든 Python 코드의 취약점을 스캔합니다
   - GitHub 보안 알림으로 의존성 취약점 검사
   - 정기적인 수동 보안 감사

2. **업데이트**
   - 보안 패치를 신속하게 적용
   - 메이저 버전은 신중하게 평가
   - 변경 이력에 보안 관련 업데이트 포함

3. **투명성**
   - 보안 업데이트를 커밋에 기록
   - 취약점 공개를 책임감 있게 처리
   - 적절한 경우 공개 보안 권고 발행

## 취약점 보고

### 우리가 다루는 보안 문제

다음 보고를 환영합니다:
- 스크립트나 예시의 **코드 취약점**
- Python 패키지의 **의존성 취약점**
- 코드 예시에 포함된 **암호화 관련 문제**
- 문서 속 **인증/인가 결함**
- 설정 예시의 **데이터 노출 위험**
- **인젝션 취약점**(SQL, 명령어 등)
- **SSRF/XXE/경로 순회** 문제

### 대상 외 보안 문제

다음은 이 프로젝트의 대상이 아닙니다:
- Claude Code 자체의 취약점(Anthropic에 보고해 주세요)
- 외부 서비스나 라이브러리의 문제(업스트림에 보고해 주세요)
- 소셜 엔지니어링이나 사용자 교육(이 가이드의 범위 밖)
- 개념 증명이 없는 이론적 취약점
- 공식 채널로 이미 보고된 의존성 취약점

## 보고 방법

### 비공개 보고(권장)

**민감한 보안 문제에는 GitHub의 비공개 취약점 보고를 사용해 주세요:**

1. 방문: https://github.com/luongnv89/claude-howto/security/advisories
2. "Report a vulnerability" 클릭
3. 취약점 세부 정보 작성
4. 다음을 포함:
   - 취약점에 대한 명확한 설명
   - 영향을 받는 컴포넌트(파일, 섹션, 예시)
   - 잠재적 영향
   - 재현 절차(해당하는 경우)
   - 권장 수정안(있다면)

**이후 진행 과정:**
- 48시간 이내에 접수를 확인합니다
- 조사하고 심각도를 평가합니다
- 수정안 개발에 협력합니다
- 공개 일정을 조율합니다
- 보안 권고에 보고자의 공로를 명시합니다(익명을 원하지 않는 한)

### 공개 보고

민감하지 않은 문제이거나 이미 공개된 문제라면:

1. **GitHub Issue를 만들고** `security` 라벨을 붙입니다
2. 다음을 포함:
   - 제목: `[SECURITY]` 뒤에 간결한 설명
   - 상세 설명
   - 영향을 받는 파일 또는 섹션
   - 잠재적 영향
   - 권장 수정안

## 취약점 대응 프로세스

### 평가(24시간)

1. 보고 접수를 확인합니다
2. [CVSS v3.1](https://www.first.org/cvss/v3.1/specification-document)로 심각도를 평가합니다
3. 대상 범위에 해당하는지 판단합니다
4. 초기 평가를 보고자에게 알립니다

### 개발(1~7일)

1. 수정안을 개발합니다
2. 수정안을 리뷰·테스트합니다
3. 보안 권고를 작성합니다
4. 릴리스 노트를 준비합니다

### 공개(심각도에 따라)

**Critical(CVSS 9.0~10.0)**
- 수정을 즉시 릴리스
- 공개 권고 발행
- 보고자에게 24시간 전 통지

**High(CVSS 7.0~8.9)**
- 48~72시간 이내에 수정 릴리스
- 보고자에게 5일 전 통지
- 릴리스와 동시에 공개 권고

**Medium(CVSS 4.0~6.9)**
- 다음 정기 업데이트에서 수정 릴리스
- 릴리스와 동시에 공개 권고

**Low(CVSS 0.1~3.9)**
- 다음 정기 업데이트에 수정 포함
- 릴리스와 동시에 권고

### 공표

다음 내용을 담은 보안 권고를 공표합니다:
- 취약점 설명
- 영향을 받는 컴포넌트
- 심각도 평가(CVSS 점수)
- 수정 버전
- 회피책(해당하는 경우)
- 보고자 공로 명시(동의한 경우)

## 보고자를 위한 모범 사례

### 보고 전

- **문제 확인:** 일관되게 재현할 수 있습니까?
- **기존 Issue 검색:** 이미 보고되지 않았습니까?
- **문서 확인:** 안전한 사용법 안내가 있습니까?
- **수정안 테스트:** 권장하는 수정안이 동작합니까?

### 보고 시

- **구체적으로:** 정확한 파일 경로와 줄 번호를 제공합니다
- **컨텍스트 포함:** 왜 이것이 보안 문제입니까?
- **영향 제시:** 공격자가 무엇을 할 수 있습니까?
- **절차 제공:** 어떻게 재현합니까?
- **수정안 제안:** 어떻게 고칩니까?

### 보고 후

- **인내심을 갖고:** 우리의 자원은 한정되어 있습니다
- **응답하기:** 후속 질문에 신속하게 답합니다
- **기밀 유지:** 수정 전에는 공개하지 않습니다
- **조율 존중:** 공개 일정을 따릅니다

## 보안 헤더와 설정

### 저장소 보안

- **브랜치 보호:** main 브랜치 변경에는 2명의 승인 필요
- **상태 검사:** 모든 CI/CD 검사 통과 필수
- **CODEOWNERS:** 주요 파일에는 지정 리뷰어
- **서명된 커밋:** 기여자에게 권장

### 개발 시 보안

```bash
# pre-commit 훅 설치
pre-commit install

# 로컬에서 보안 스캔 실행
bandit -c pyproject.toml -r scripts/
mypy scripts/ --ignore-missing-imports
ruff check scripts/
```

### 의존성 보안

```bash
# 알려진 취약점 검사
pip install safety
safety check

# 또는 pip-audit 사용
pip install pip-audit
pip-audit
```

## 기여자를 위한 보안 가이드라인

### 예시를 작성할 때

1. **시크릿을 하드코딩하지 않습니다**
   ```python
   # ❌ 나쁜 예
   api_key = "sk-1234567890"

   # ✅ 좋은 예
   api_key = os.getenv("API_KEY")
   ```

2. **보안 영향을 경고합니다**
   ```markdown
   ⚠️ **보안 참고 사항**: `.env` 파일은 절대 git에
   커밋하지 마세요. 바로 `.gitignore`에 추가하세요.
   ```

3. **안전한 기본값을 사용합니다**
   - 인증을 기본으로 활성화합니다
   - 해당하는 경우 HTTPS를 사용합니다
   - 입력을 검증·정제합니다
   - 매개변수화된 쿼리를 사용합니다

4. **보안 고려 사항을 문서화합니다**
   - 왜 보안이 중요한지 설명합니다
   - 안전한 패턴과 안전하지 않은 패턴을 보여 줍니다
   - 신뢰할 수 있는 출처로 링크합니다
   - 경고를 눈에 띄게 적습니다

### 기여를 리뷰할 때

1. **노출된 시크릿 검사**
   - 일반적인 패턴 스캔(api_key=, password= 등)
   - 설정 파일 리뷰
   - 환경 변수 확인

2. **안전한 코딩 관행 확인**
   - 인증 정보 하드코딩이 없는가
   - 입력 검증이 적절한가
   - 인증/인가가 안전한가
   - 파일 처리가 안전한가

3. **보안 영향 테스트**
   - 악용될 가능성이 있는가?
   - 최악의 경우는?
   - 엣지 케이스는 있는가?
