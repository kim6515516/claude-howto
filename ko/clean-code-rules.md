# AI 코드 생성을 위한 클린 코드 규칙

이 규칙들은 유지 보수가 가능하고 전문가 수준의 코드를 생성하기 위한 코드 생성 지침입니다.

## 의미 있는 이름
- 무엇을 위해 존재하는지 드러내는, 의도가 분명한 이름을 사용합니다
- 오해를 부르는 표현이나 의미 없는 구분(예: `data`, `info`, `manager`)을 피합니다
- 발음할 수 있고 검색할 수 있는 이름을 사용합니다
- 클래스 이름: 명사(예: `UserAccount`, `PaymentProcessor`)
- 메서드 이름: 동사(예: `calculateTotal`, `sendEmail`)
- 머릿속 매핑이나 인코딩(헝가리안 표기법, 접두사)을 피합니다

## 함수
- 함수는 작게 유지합니다(이상적으로는 20줄 미만)
- 한 가지 일만 합니다 — 단일 책임 원칙
- 함수 하나에 추상화 수준은 하나
- 인자를 제한합니다: 이상적으로는 0~2개, 최대 3개, 플래그 인자는 피합니다
- 부작용을 만들지 않습니다 — 함수는 이름 그대로의 일만 합니다
- 명령(상태를 바꾸는 것)과 질의(정보를 반환하는 것)를 분리합니다
- 에러 코드보다 예외를 사용합니다

## 주석
- 코드는 스스로를 설명해야 합니다 — 가능한 한 주석을 피합니다
- 좋은 주석: 법적 정보, 경고, TODO, 공개 API 문서
- 나쁜 주석: 중복되거나, 오해를 부르거나, 나쁜 코드에 대한 변명
- 코드를 주석 처리하지 않습니다 — 삭제합니다(이력은 버전 관리가 보관합니다)
- 주석이 필요하다고 느껴지면 대신 코드 리팩터링을 검토합니다

## 포맷
- 파일은 작고 초점이 맞게 유지합니다
- 세로 포맷: 관련 개념은 가까이에, 개념 사이는 빈 줄로 구분합니다
- 가로 포맷: 줄 길이를 제한합니다(80~120자)
- 일관된 들여쓰기와 팀 스타일을 사용합니다
- 관련 함수는 가까이에 모읍니다

## 객체와 자료 구조
- 객체: 데이터를 추상화 뒤에 숨기고 메서드를 통해 동작을 노출합니다
- 자료 구조: 데이터를 노출하고 동작은 최소한으로 억제합니다
- 디미터 법칙: 직접적인 친구에게만 말을 겁니다(`a.getB().getC().doSomething()`을 피합니다)
- 게터/세터로 내부 구조를 무분별하게 노출하지 않습니다

## 에러 처리
- 반환 코드나 에러 플래그 대신 예외를 사용합니다
- 실패할 가능성이 있는 코드는 `try-catch-finally`를 먼저 작성합니다
- 예외 메시지에는 컨텍스트를 포함합니다
- `null`을 반환하지 않습니다 — 빈 컬렉션을 반환하거나 Optional/Maybe를 사용합니다
- `null`을 인자로 넘기지 않습니다

## 클래스
- 작은 클래스: 줄 수가 아니라 책임의 수로 측정합니다
- 단일 책임 원칙: 변경할 이유가 하나뿐
- 높은 응집도: 많은 메서드에서 쓰이는 클래스 변수
- 낮은 결합도: 클래스 간 의존 관계를 최소화합니다
- 개방/폐쇄 원칙: 확장에는 열려 있고 수정에는 닫혀 있습니다

## 단위 테스트
- Fast, Independent, Repeatable, Self-validating, Timely(F.I.R.S.T.)
- 테스트 하나에 단언 하나(또는 개념 하나)
- 테스트 코드의 품질은 프로덕션 코드와 동등합니다
- 무엇을 테스트하는지 알 수 있는 읽기 쉬운 테스트 이름
- Arrange-Act-Assert 패턴

## 코드 품질 원칙
- **DRY(Don't Repeat Yourself):** 중복을 만들지 않습니다
- **YAGNI(You Aren't Gonna Need It):** 가상의 미래를 위해 만들지 않습니다
- **KISS(Keep It Simple):** 불필요한 복잡함을 피합니다
- **보이스카우트 규칙:** 처음 발견했을 때보다 깨끗한 상태로 코드를 떠납니다

## 피해야 할 코드 스멜
- 긴 함수나 클래스
- 중복 코드
- 죽은 코드(사용하지 않는 변수, 함수, 인자)
- 기능 욕심(다른 클래스에 지나치게 관심을 갖는 메서드)
- 부적절한 친밀함(클래스끼리 서로를 너무 많이 아는 것)
- 긴 인자 목록
- 원시 타입 집착(작은 객체 대신 원시 타입을 남용하는 것)
- switch/case 문(다형성을 검토합니다)
- 임시 필드(가끔씩만 쓰이는 클래스 변수)

## 동시성
- 동시성 코드를 다른 코드와 분리합니다
- 동기화/잠금 대상 데이터의 범위를 제한합니다
- 스레드 안전한 컬렉션을 사용합니다
- 동기화 구간은 작게 유지합니다
- 실행 모델과 프리미티브를 이해합니다

## 시스템 설계
- 생성과 사용을 분리합니다(의존성 주입)
- 복잡한 객체 생성에는 팩토리나 빌더를 사용합니다
- 구현이 아니라 인터페이스에 맞춰 프로그래밍합니다
- 상속보다 합성을 우선합니다
- 디자인 패턴은 과시용이 아니라 단순화에 도움이 될 때 적용합니다

## 리팩터링
- 큰 덩어리가 아니라 지속적으로 리팩터링합니다
- 전후로 항상 테스트가 통과하는 상태를 유지합니다
- 작은 단계: 한 번에 하나씩 변경
- 일반적인 리팩터링: Extract Method, Rename, Move, Inline

## 문서
- 스스로를 설명하는 코드 > 주석 > 외부 문서
- 공개 API에는 명확한 문서가 필요합니다
- 문서에는 예시를 포함합니다
- 문서는 코드 가까이에 둡니다(이상적으로는 코드 안에)

---

**핵심 철학:** 코드는 쓰이는 횟수의 10배만큼 읽힙니다. 영리함이 아니라 가독성과 유지 보수성을 최적화합니다.
